# Отчет по нагрузочному тестированию
Проведено нагрузочное тестирование трёх эндпоинтов:
- **Team endpoints** (управление командами)
- **PR endpoints** (получение ревью пользователей)
- **Mixed workload** (комплексная нагрузка на различные эндпоинты)

**Общий результат:** все тесты пройдены успешно со 100% доступностью

---

## 1. Тестирование Team Endpoints

### Параметры теста
- **Endpoint:** `GET /team/get`
- **Длительность:** 10 секунд
- **Частота запросов:** 50 req/s
- **Всего запросов:** 500

### Результаты

| Метрика | Значение |
|---------|----------|
| **Общее количество запросов** | 500 |
| **Успешных запросов** | 500 (100%) |
| **Throughput** | 50.09 req/s |
| **Средняя латентность** | 3.418 ms |
| **Медианная латентность (p50)** | 2.967 ms |
| **90-й перцентиль (p90)** | 5.637 ms |
| **95-й перцентиль (p95)** | 6.836 ms |
| **99-й перцентиль (p99)** | 12.034 ms |
| **Минимальная латентность** | 700.75 µs |
| **Максимальная латентность** | 16.277 ms |

### Анализ

**Положительные моменты:**
- 100% доступность без ошибок
- Стабильная средняя латентность ~3.4 ms
- Низкая вариативность латентности (медиана близка к среднему)
- Даже 99-й перцентиль остается в пределах 12 ms

**Производительность:**
- Эндпоинт `/team/get` показывает отличную производительность
- Среднее время ответа составляет менее 3.5 ms, что является превосходным показателем
- Отсутствие выбросов (max 16.277 ms при p99 12.034 ms)

## 2. Тестирование PR Endpoints

### Параметры теста
- **Endpoint:** `GET /users/getReview`
- **Длительность:** 10 секунд
- **Частота запросов:** 50 req/s
- **Всего запросов:** 500
- **Подготовка:** Создано 5 Pull Requests

### Результаты

| Метрика | Значение |
|---------|----------|
| **Общее количество запросов** | 500 |
| **Успешных запросов** | 500 (100%) |
| **Throughput** | 50.08 req/s |
| **Средняя латентность** | 3.481 ms |
| **Медианная латентность (p50)** | 3.031 ms |
| **90-й перцентиль (p90)** | 5.899 ms |
| **95-й перцентиль (p95)** | 7.067 ms |
| **99-й перцентиль (p99)** | 12.966 ms |
| **Минимальная латентность** | 806.291 µs |
| **Максимальная латентность** | 19.079 ms |

### Анализ

**Положительные моменты:**
- 100% доступность без ошибок
- Производительность практически идентична team endpoints
- Больший размер ответа (508 bytes vs 286 bytes) не привел к значительному снижению производительности

**Сравнение с Team Endpoints:**
- Латентность выше всего на 0.063 ms (1.8% разница)
- Размер ответа в 1.77 раз больше
- Максимальная латентность чуть выше (19.079 ms vs 16.277 ms)

**Производительность:**
- Эндпоинт работы с Pull Requests демонстрирует отличную производительность
- Более сложная бизнес-логика (получение списка PR для пользователя) обработана эффективно

## 3. Комплексное тестирование (Mixed Workload)

### Параметры теста
- **Endpoints:** 
  - `GET /health` (×2)
  - `GET /team/get` (×3 команды)
  - `GET /users/getReview` (×3 пользователя)
- **Длительность:** 30 секунд
- **Частота запросов:** 100 req/s (удвоенная нагрузка)
- **Всего запросов:** 3000
- **Подготовка:** 3 команды, 10 Pull Requests

### Результаты

| Метрика | Значение |
|---------|----------|
| **Общее количество запросов** | 3000 |
| **Успешных запросов** | 3000 (100%) |
| **Throughput** | 100.03 req/s |
| **Средняя латентность** | 2.789 ms |
| **Медианная латентность (p50)** | 2.522 ms |
| **90-й перцентиль (p90)** | 4.552 ms |
| **95-й перцентиль (p95)** | 5.647 ms |
| **99-й перцентиль (p99)** | 9.763 ms |
| **Минимальная латентность** | 497.959 µs |
| **Максимальная латентность** | 28.315 ms |
| **Общее время обработки** | 8.366 секунд |

### Анализ

**Ключевые наблюдения:**
- **100% доступность** при удвоенной нагрузке (100 req/s)
- **Улучшенная средняя латентность** (2.789 ms vs 3.4+ ms в отдельных тестах)
- Минимальная латентность снижена почти вдвое (497 µs)
- Максимальная латентность выросла до 28.315 ms 

**Эффект масштабирования:**
- При увеличении нагрузки в 2 раза (с 50 до 100 req/s) средняя латентность **улучшилась** на 18%
- Это указывает на эффективное использование ресурсов и оптимизацию под нагрузкой
- Возможные причины: better connection pooling, warm caches, optimized database queries
